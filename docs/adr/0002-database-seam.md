# A Database seam replaces the AppDatabase singleton

All persistence flowed through `AppDatabase.instance`, a static singleton read directly by the list providers and by five screens (single-entity loads, reorder write-loops, the Character autosave). A static global has no substitution point, so nothing above the database was testable and the suite was a single pure-model file. We extract a `Database` interface — the ~25 async CRUD methods `AppDatabase` already exposes — publish it as a Riverpod `databaseProvider`, and route every caller through that provider. The real SQLite code becomes `SqfliteDatabase implements Database`; a behavioral `InMemoryDatabase` fake becomes the test-only second adapter. `AppDatabase.instance` is deleted. The change is behavior-preserving: no schema change, no migration, no user-visible difference.

## Considered Options

- **Per-aggregate repositories** (`CampaignRepository`, `CharacterRepository`, ...) instead of one interface — rejected for now. C2's goal is a testable seam, not decomposing the data layer. Five interfaces plus five providers is 5× the wiring on the one change everything else depends on, and today's code has no per-aggregate seam to hang them on. Aggregates already get locality via the `─── Characters ───` sections inside the single class. Splitting stays available later if a family grows real logic.
- **Constructor injection** of the `Database` into each notifier — rejected in favor of `ref.read(databaseProvider)`. Constructor injection fights Riverpod's `.new` tear-off notifier construction and adds family plumbing for no payoff; `ref` is already in scope. `read`, not `watch`, because the database instance is stable and must not trigger rebuilds.
- **Doing C4 (single-item providers) inside this change** — rejected as scope blow-up. The five screens instead swap `AppDatabase.instance` for `ref.read(databaseProvider)` (all are already `ConsumerState`), killing the static global while leaving the direct single-entity reads in place. Replacing those with `ref.watch(entityProvider)` is C4, which depends on this seam.
- **Exposing lifecycle (`init`/`open`/`close`) on the interface** — rejected in favor of pure CRUD. The lazy-open, ffi init, and path resolution stay private inside `SqfliteDatabase`; callers never reason about connection lifecycle, and the fake needs no open step. This keeps the interface deep (thin surface, wide hidden implementation).
- **Adding a transaction/batch primitive now** to enable atomic reorder — rejected. This change mirrors today's CRUD exactly; the reorder write-loops stay N update calls through the seam. The shape of an atomic-reorder operation is C3's decision and is not pre-installed speculatively.
- **A canned-response stub for the test double** — rejected in favor of a behavioral `InMemoryDatabase`. A stub only proves "the notifier called `getX`". The fake instead reproduces the real adapter's ordering (`name ASC`, `updated_at DESC`, `order_index ASC`) and foreign-key filtering, so a passing test reflects how production actually reads.

## Consequences

- **`databaseProvider` is the single test seam.** A test overrides it with an `InMemoryDatabase` in a `ProviderContainer`/`ProviderScope` and asserts notifier behavior with no real SQLite and no widget pump. It sits above both providers and screens, so one override point covers every caller. This is the first provider-level test in the repo; `test/models/component_test.dart` remains the prior art for pure-Dart, no-Flutter discipline.
- **Cascade delete is not simulated by the fake.** `SqfliteDatabase` relies on SQLite `ON DELETE CASCADE`; a map-backed fake cannot reproduce it without reimplementing SQLite. `InMemoryDatabase` deliberately omits cascade, so deletion-cascade behavior is *not* asserted at the fake seam — it belongs to a real-adapter/integration test if it needs coverage. This is the sharpest divergence risk between the two adapters and is accepted knowingly.
- **The `InMemoryDatabase` fake must stay aligned with the real adapter's query semantics.** Its ordering and filtering are duplicated from `SqfliteDatabase`'s `orderBy`/`where` clauses; if the real adapter's sort or filter changes, the fake must change with it or tests will pass against a fiction.
- **`InMemoryDatabase` lives under `test/`**, not `lib/`, so the shipped bundle contains no test double and no production code can depend on a fake.
- **This seam is the prerequisite for C3, C4, and C6.** Reorder atomicity, single-item providers, and schema migrations all become buildable-and-testable behind `Database`. In particular it unblocks the migration path that [ADR-0001](0001-typed-component-data.md) assumes: ADR-0001 freezes the `dbKey` strings precisely because no migration path existed; a testable `Database` seam (with an in-memory adapter to dry-run migrations against) is what makes changing a frozen `dbKey` conceivable later. `onUpgrade` itself remains absent — adding it is C6.
