# Foreign keys are enforced on the connection, and orphaned rows are swept once

The v1 DDL declared `FOREIGN KEY … ON DELETE CASCADE` on `chapters`, `session_screens` and `components`, and nothing ever enabled enforcement. SQLite leaves foreign keys off by default and the setting is per *connection*, not stored in the file, so those clauses were decorative for the whole life of the schema: verified through `openAppDatabase` — the function `SqfliteDatabase` opens its real database with — `PRAGMA foreign_keys` read back `0`, deleting a Campaign left its Chapter, SessionScreen and SessionComponent rows behind at all three levels, and inserting a Chapter whose `campaign_id` matched no Campaign was accepted. The second and third of those are separate defects: the first is a missing cascade, the second is the absence of referential integrity altogether. We enable enforcement in the connection's `onConfigure` hook, and add migration step 4 to delete the rows already orphaned on disk.

`onConfigure` is the hook and not a `Migrations` step, because a step runs once at a version change while the pragma has to be set on every open — a test asserts that a database reopened after the pragma was set reads `0` again, so the distinction is checked rather than assumed. `sqflite`'s documented callback order is `onConfigure` → `onCreate`/`onUpgrade` → `onOpen`, and its source invokes `onConfigure` before the version check and outside the version-change transaction, which matters because SQLite treats the pragma as a no-op inside a transaction.

Step 4 deletes, in this order, Chapters with no Campaign, SessionScreens with no Chapter, and SessionComponents with no SessionScreen. The order is load-bearing and deliberately does not lean on the cascade it is there to make honest: removing orphaned Chapters is what turns their SessionScreens into orphans for the next statement to catch. The predicate is `NOT EXISTS`, not `NOT IN`, because `NOT IN` yields no rows at all when any parent id is NULL and SQLite permits NULL in a TEXT PRIMARY KEY.

Opening the database is now reachable from tests. `openAppDatabase(path)` holds the version, the configure hook and the ladder wiring; `SqfliteDatabase` resolves the on-device path and calls it. A test that re-listed those options itself would prove something about the test, not about the app — which is the whole reason the original defect survived so long unnoticed.

## Considered Options

- **The pragma as a statement in a migration step** — rejected, and disproven rather than argued away. A step runs once when the schema version changes; connection state does not persist, so the next launch would open unprotected while the ladder reported the migration as applied. The test asserting that a reopened database reads `foreign_keys = 0` exists to keep anyone from trying this again.
- **Executing the pragma lazily on first query, inside the adapter's `_conn` getter** — rejected. It would run after `onCreate`/`onUpgrade` had already executed, leaving migrations — the code most likely to move rows in bulk — as the one place still running unprotected. `onConfigure` runs first by contract.
- **Dropping the `ON DELETE CASCADE` clauses instead and deleting children explicitly in each `deleteX` method** — rejected. It is the same behaviour written three times in Dart instead of once in the schema, it puts the invariant where a future caller can forget it, and it would still leave a database that accepts a child row pointing at a parent that does not exist.
- **Enabling enforcement but leaving existing orphans in place** — rejected. It would leave installed databases permanently contradicting the constraints they now declare, and the rows serve no one: every read descends from a parent id (`getChapters(campaignId)` and its siblings), so no orphan has ever been visible to a DM. Leaving invisible rows that fail `PRAGMA foreign_key_check` is a trap for the next person who runs it or attempts a table rebuild.
- **Sweeping orphans at app startup rather than in a migration step** — rejected. It would run the sweep on every launch forever to fix a condition that can only exist once, and put a destructive write outside the transactional, versioned mechanism that exists precisely to carry destructive writes.
- **Shipping enforcement without the sweep and letting the data-transfer work clean up implicitly** — rejected. Import in that feature does delete unreachable orphans as a side effect, but relying on it would make correctness here depend on a user performing an unrelated action in a feature that does not exist yet.
- **A `foreign_key_check` assertion at startup that surfaces violations to the user** — rejected as scope creep. It reports a problem this decision removes, and there is no action a player or DM could take in response.

## Consequences

- **Deletion semantics changed app-wide, and this is the point rather than a side effect.** Deleting a Campaign now removes its Chapters, their SessionScreens and their SessionComponents; deleting a Chapter or a SessionScreen cascades likewise. Every existing test still passes, including the atomic reorder suite (ADR-0003) and the migration execution test (ADR-0005), which now run with enforcement on.
- **Writes that were silently accepted can now throw.** Inserting or updating a child row whose parent id does not exist raises a `DatabaseException` instead of writing an unreachable row. Nothing in the app writes such a row today — every insert path goes through a parent screen — so no caller changes here, but a future caller that manufactures ids out of order will now find out immediately instead of producing invisible data.
- **`INSERT OR REPLACE` on a parent table had to go, and this was found by probing rather than by reasoning.** REPLACE resolves a primary key conflict by deleting the existing row first; with enforcement on, that delete cascades. A probe confirmed it: re-inserting a Chapter under its own id left its SessionScreen and SessionComponent counts at zero. The inserts for `campaigns`, `chapters` and `session_screens` therefore drop the replace policy and let a duplicate id throw, which no caller triggers today — every `add` mints a fresh uuid and every edit goes through `update`. `characters` and `components` keep it: they have no children, so there is nothing for a cascade to take, and changing them would be an unmotivated behaviour change. A characterization test pins the destructive behaviour in place so that reintroducing the policy on a parent table is a visible choice rather than an accident.
- **The adapter's own conflict policy is still not directly assertable.** The tests reach `openAppDatabase`, but `SqfliteDatabase`'s CRUD methods resolve their path through `path_provider`, which has no implementation in a `flutter test` process — so "`insertChapter` does not replace on conflict" is verified at the SQL level, one layer below the method that must honor it. Making the adapter's path injectable would close that gap and is not done here.
- **Step 4 is this ladder's first step to delete user rows.** Earlier steps only shaped the schema. ADR-0005 anticipated row-level SQL; what it demands of a step like this is an exact predicate and a written reason, both of which sit beside the statements. The step is a no-op on a database with no orphans, so a fresh install and an upgraded one still end up identical.
- **The requested schema version moved from 3 to 4, and is still a literal repeated outside the ladder.** Appending this step meant editing that literal by hand — exactly the divergence the `data-transfer` prefactor ticket exists to remove. That ticket is now better motivated, not obsolete.
- **ADR-0005's "the module stays entirely inside `SqfliteDatabase`" is narrowed, not contradicted.** The ladder wiring moved out of the class and into `openAppDatabase`, a top-level function in the same library. What ADR-0005 was refusing — putting `Migrations` *above* the `Database` seam, where `InMemoryDatabase` would have to care about a schema it does not have — still holds: the seam interface is untouched, the fake knows nothing about migrations, and `Migrations` remains a SQLite-only concern below the seam. Read ADR-0005's sentence as "not above the seam", which is the reason it gave, rather than "inside that class", which was only where it happened to live. `openAppDatabase` takes nothing but a path, so no caller can vary the ladder.
- **`openAppDatabase` is public API of the database module.** The seam of ADR-0002 is unchanged — `Database` gained no method and `InMemoryDatabase` is untouched — but the SQLite adapter's open configuration is now a named, callable thing rather than a private closure. The cost is one more public name; the benefit is that "how the app opens its database" is assertable, which it was not when this defect was introduced.
- **This is the suite's second test file that opens a real SQLite database**, after the migration execution test ADR-0005 introduced as a deliberate exception to the pure-test rule. The same justification holds and is not weaker for being reused: connection configuration has no pure-Dart surface at all — `InMemoryDatabase` has no connection to configure — so there is no fake against which "foreign keys are enforced" could even be stated.
- **How long the defect lasted is itself the lesson.** The schema declared an intent, the code never carried it out, and no test could catch the gap because every test either avoided the database or built its own connection. Configuration that only matters in production needs a seam through which production's own configuration can be observed.
- **Not addressed:** `onDowngrade` is still undefined, `PRAGMA foreign_key_check` is never run, and no other pragma (journal mode, synchronous) is set. None are precluded; `onConfigure` is now the obvious place for any of them.
