# A declarative migration ladder replaces the absent onUpgrade path

`SqfliteDatabase` opened the on-device database at schema version 1 through a single `onCreate`, with no `onUpgrade` defined. That gap meant the first schema change would either crash the app at startup for every existing install (`sqflite` throws once the on-disk version and the requested version disagree with no `onUpgrade` to reconcile them) or leave stale schema in place while new code assumed columns that were never created. ADR-0001 froze the `dbKey` strings persisted in `components.type` precisely because of this gap. We add a `Migrations` module owning an ordered ladder of steps — each step a schema version plus the SQL statements that carry a database from the version below it up to that one. Selecting which steps apply between two versions, `stepsFrom(oldVersion, newVersion)`, is a pure function that touches no database, so step selection is fully testable dry. `onCreate` and `onUpgrade` are both redefined as callers of the same ladder — "apply every step from 0" and "apply every step above the old version" respectively — so a freshly created database and a migrated one are always built by the identical code path. The current `onCreate` DDL becomes the ladder's first step, version 1; production ships exactly that one step and the schema version does not change. Each upgrade runs inside a single transaction, so a failed migration leaves the database at its previous version rather than half-migrated.

## Considered Options

- **Steps as Dart callbacks receiving the open connection** — rejected. It couples the `Migrations` module directly to `sqflite`'s connection type and defeats the goal of testing step selection with no database open; a callback can do anything, so it can't be reasoned about or asserted on without executing it.
- **A hybrid shape — steps as SQL by default, with an escape hatch to a Dart callback** — rejected for now. It gives two ways to write a migration on day one with no concrete migration yet demanding the callback form. The consequence of staying purely declarative is accepted explicitly below rather than pre-solved speculatively.
- **Shipping a real v2 schema change alongside the mechanism**, to prove it against an actual need — rejected. Nothing on the roadmap demands a schema change today; inventing one to exercise the code would be scope creep with no user-facing justification. The mechanism is instead proven with a test-owned fake ladder.
- **Testing only `stepsFrom` (step selection) and treating execution as self-evident** — rejected. Step selection is the easy half; the half that can actually destroy a user's database is the transaction executing SQL against a live file. Skipping an execution test would leave exactly that risk unverified.
- **Keeping `onCreate` and `onUpgrade` as two hand-maintained code paths**, with `onUpgrade` simply added alongside the existing `onCreate` — rejected. Two paths invite drift: a step added to one and forgotten in the other produces a fresh install and a migrated install with different schemas, silently. Routing both through the same ladder makes that class of bug structurally impossible rather than a matter of code-review discipline.
- **Putting the `Migrations` module above the `Database` seam**, e.g. exposed as part of the interface — rejected. Migrations are a SQLite-specific concern (`sqflite`'s `onCreate`/`onUpgrade` hooks); `InMemoryDatabase` has no schema to migrate. The module stays entirely inside `SqfliteDatabase`, and the `Database` interface is unchanged.

## Consequences

- **A migration needing Dart-side data transformation does not fit today.** Rewriting a JSON payload embedded in an existing row — for example, migrating `components.data` to a renamed `dbKey` — is not expressible as a step under this design; only DDL and row-level SQL `UPDATE`/backfill are. The shape gets extended when a real case demands it, not ahead of one. Until then, ADR-0001's frozen `dbKey`s remain frozen in practice even though a migration *path* now exists — this ADR unblocks the *mechanism*, not the rename itself.
- **`onCreate` and `onUpgrade` can never drift apart.** Because both are thin callers of the same `stepsFrom` ladder, a freshly installed database and one upgraded from v1 are provably built by identical DDL. This is checked directly in tests, not just true by code inspection.
- **This is the repo's first test suite that opens a real SQLite database.** Every prior test (`test/models/component_test.dart`, the `test/providers/*_test.dart` family from ADR-0002) is pure Dart with no I/O. The migration execution test, run against `sqflite_common_ffi`'s in-memory database, is a deliberate, documented exception — it exists because step selection alone cannot prove that data actually survives an upgrade.
- **No production schema change ships with this decision.** The ladder holds exactly one step — the current v1 DDL, verbatim — so this change is behavior-preserving for every existing install. The value delivered is the tested mechanism, ready for the next schema change to use.
- **Downgrade, rollback, backup, and export remain unaddressed.** The ladder only ever moves forward; none of those are this decision's concern, and none are precluded by it.
- **Migrations stay below the `Database` seam.** `InMemoryDatabase` and the `Database` interface from ADR-0002 are untouched, keeping the seam's promise that adapters are free to differ in implementation detail as long as they honor the same contract.
