# Single-item providers replace per-screen setState loads

Five screens each loaded their own entity by calling the parent-collection list query through the `Database` seam, filtering the result in memory for the one row their route id named, and holding it in `setState` for the screen's lifetime. That copy sat outside the Riverpod provider graph, so nothing invalidated it after a mutation made anywhere else — most visibly in PG Mode, where `CharacterSheetScreen` debounce-saves the Character directly through the seam and leaves `characterListProvider` stale. We add four single-item providers — `campaignProvider`, `chapterProvider`, `screenProvider`, `characterProvider` — each an `AsyncNotifierProvider.family<..., String>` keyed by entity id, whose `build(id)` reads one entity through the seam and whose `save(entity)` writes it, invalidates itself, and invalidates the parent list provider's matching family entry. The `Database` interface gains `getChapter(String id)` and `getScreen(String id)` to give the two new families a single-entity read to call (`getCampaign` and `getCharacter` already existed). The five screens replace their `initState`-driven loads with `ref.watch(xProvider(id))`. Every update of an *existing* entity now goes through its single-item provider's `save()`; list notifiers keep collection-shaped operations only (`add`, `delete`, C3's `reorder`).

## Considered Options

- **Read-only `FutureProvider.family` per entity** instead of an `AsyncNotifierProvider` — rejected. A read-only provider has no `save()` of its own, so mutations would have stayed on the list notifiers exactly as today, and two places (list notifier, single-item provider) would need to keep invalidating each other in perpetuity. An `AsyncNotifierProvider` gives each entity exactly one write path that owns its own invalidation.
- **A `componentProvider` for symmetry with the other four entities** — rejected. SessionComponent has no route id of its own and no dedicated screen; it is always rendered as part of `componentListProvider(screenId)`. Adding a single-item provider with nothing to key it from a route would be a provider with no natural caller. Component saves keep going through `componentListProvider(screenId).notifier.save(c)`.
- **Leaving mutations on the list notifiers and having single-item providers merely re-read after a list invalidation** — rejected as the same two-sources-of-truth problem in a different shape: a caller would still need to know to invalidate both, and a caller that saved through the list notifier without knowing about the single-item provider would reintroduce staleness for anything watching the single-item provider instead.
- **Splitting the `Database` seam into per-aggregate repositories while adding the two new read methods** — rejected as scope blow-up, consistent with ADR-0002's decision to keep one interface. `getChapter`/`getScreen` are added to the existing single `Database` interface, mirroring the shape `getCampaign`/`getCharacter` already had.
- **Treating a missing entity as an exception** — rejected. All four single-item reads return a nullable entity; a screen opened after its entity was cascade-deleted elsewhere (e.g. its parent Chapter or Campaign was removed) is a legitimate state the screen must render, not a crash.
- **Having `SessionPlayScreen` also watch `screenProvider(screenId)` for the currently displayed screen** — rejected as redundant. The screen already watches `screenListProvider(chapterId)` for pagination across all of a chapter's screens; deriving the current SessionScreen from that list (keeping only the page index as local state) is a strictly more complete source for what this screen needs and avoids watching two providers for overlapping data.

## Consequences

- **One writer per entity, no cross-invalidation to remember.** Renaming a Chapter or SessionScreen, editing Campaign info, and the Character autosave all move from list-notifier `save()` calls or a direct seam write (`CharacterSheetScreen._saveNow`) onto the matching single-item provider's `save()`. This is the direct fix for the staleness bug: a save is visible everywhere a Riverpod consumer watches that entity, by construction, not by convention.
- **List notifiers shrink to collection operations only.** `campaignListProvider`, `chapterListProvider`, and `screenListProvider` keep `add`/`delete` (and, from C3, `reorder`); their `save()` methods either go away or are no longer the call site any screen uses for an existing-entity update. `componentListProvider` is unaffected and keeps its existing `save()`, since SessionComponent has no single-item provider.
- **Five screens lose their `setState`-held entity field.** `CampaignScreen`, `ChapterScreen`, `SessionEditScreen`, and `CharacterSheetScreen` render `ref.watch(xProvider(id))`'s `AsyncValue` (loading / error / missing / data) instead of an `initState`-populated nullable field. `SessionPlayScreen` is the one exception: it keeps deriving its current screen from `screenListProvider(chapterId)`, with only the page index as local UI state, since it needs the full ordered list for pagination regardless.
- **The `Database` interface grows by two methods**, both implemented in `SqfliteDatabase` (a `where: 'id = ?'` query, matching `getCampaign`/`getCharacter`) and in `InMemoryDatabase` (a map lookup, matching the same two). No schema or DDL change; this is additive to the seam's read surface only.
- **`CharacterSheetScreen`'s debounce timing is unaffected.** Only the write target inside `_saveNow()` changes, from `ref.read(databaseProvider).updateCharacter(...)` to `characterProvider(id).notifier.save(...)`; the 600ms `Timer` debounce and the dispose-time flush are untouched.
- **This unblocks C7.** Decomposing `CharacterSheetScreen`'s seven tabs depends on the screen's save path already being routed through `characterProvider`, so C7 does not have to fix the write path and the tab structure in the same change.
- **Depends on ADR-0002's `Database` seam** (`databaseProvider`) as its test and injection point; the same `ProviderContainer` + `InMemoryDatabase` pattern used for the list notifiers is reused for the four new families with no new test seam introduced.
