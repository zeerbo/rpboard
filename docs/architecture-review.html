Problem
Due rappresentazioni parallele dello stesso payload: il Map non tipizzato è live, la sealed class ComponentData è dead code — la forma di ogni kind è scritta 3 volte (defaults, fromJson, toJson) e dispatchata da 5 switch.
Solution
Sostituire SessionComponent.data con ComponentData, spostare ComponentDefaults dentro ogni subclass come factory empty(), eliminare l'enum ComponentType; dbKey resta la stringa persistita.
  • locality: un kind = un file, una classe
  • leverage: il compilatore forza l'esaustività
  • l'interface si restringe, l'implementation assorbe i 5 switch
  • il test esistente smette di testare dead code
  • UnknownComponentData smette di essere teorico
  • nessuna migration DB: dbKey == enum.name
Allineato ad ADR-0001 — non lo contraddice, lo completa. Punti 1 e 2 di "Known gaps" chiusi insieme.

Problem
AppDatabase.instance è un singleton statico letto direttamente da 5 screens oltre che dai providers: non esiste un seam dove sostituire la persistence, quindi niente di sopra è testabile e la suite si ferma a 1 file su dead code.
Solution
Estrarre l'interface (5 famiglie CRUD), esporla come databaseProvider Riverpod, iniettarla nei notifier via ref.read; le screens smettono di parlare col DB e passano dai providers.
  • due adapter reali giustificano il seam
  • l'interface diventa la test surface
  • locality: accesso ai dati in un solo strato
  • widget test possibili con ProviderScope(overrides:)

C3 — Un module per il riordino ordinato

Strong in-process

campaign_screen.dart:187 · chapter_screen.dart:132 · session_edit_screen.dart:162-171

After — un deep module, 3 call site

campaign

reorder<T extends Ordered>(list, old, new)
— reindex in memoria
— una transaction
— restituisce la nuova lista
Problem
Il riordino è copiato in 3 screens, muta in place la lista posseduta dal provider e scrive N righe senza transaction: un crash a metà lascia gli order_index incoerenti.
Solution
Un module reorder generico su un contratto Ordered (id + order), con la scrittura in una sola transaction dietro l'interface della persistence.
  • leverage: una interface, 3 call site
  • locality: i bug di ordinamento in un module
  • testabile senza Flutter
  • scrittura atomica, niente stato incoerente

C4 — Single-item provider per Campaign / Chapter / SessionScreen

Worth exploring in-process

campaign_screen.dart:46 · chapter_screen.dart:37 · session_edit_screen.dart:41 · session_play_screen.dart:42 · character_sheet_screen.dart:44,116

Before — due sorgenti di verità

sequenceDiagram

  participant DB as AppDatabase
  S->>DB: getScreens(chapterId)
  DB-->>S: List (filtra in memoria)

non si invalida mai

After — una sola sorgente

sequenceDiagram
  participant S as SessionEditScreen
  participant P as screenProvider(screenId)
  participant DB as Database seam
  S->>P: watch
  P->>DB: getScreen(id)
  DB-->>P: SessionScreen
  P-->>S: AsyncValue
  Note over S,P: invalidate ⇒ la UI si aggiorna
Problem
Ogni screen carica la propria entità in initState con una query di lista filtrata in memoria e la tiene in setState: stato duplicato fuori dal grafo Riverpod, che dopo una mutazione resta stale (visibile su CharacterSheetScreen, che salva col debounce direttamente sul DB e lascia characterListProvider indietro).
Solution
Aggiungere provider family per singola entità (campaignProvider, chapterProvider, screenProvider, characterProvider) e far passare da lì anche i salvataggi.
  • locality: un'entità, una sorgente
  • elimina il pattern informale initState + DB
  • niente liste caricate per leggere 1 riga
  • dipende da C2 (serve il seam)

C6 — Percorso di migration dello schema

Strong local-substitutable

lib/core/database/db.dart:30-138

Before — un solo gradino

onUpgrade: assente

Il DB dell'utente è già sul disco. Prima modifica di schema ⇒ dati inaccessibili o app che crasha all'avvio.

After — scala di migration

v1 → v2 · migration step
v2 → v3 · migration step
Migrations.runFrom(oldV, newV)
lista ordinata, testabile a secco
Problem
Schema v1 senza onUpgrade: qualsiasi cambio di schema futuro rompe i DB già installati, e ADR-0001 congela i dbKey proprio perché quel percorso non esiste.
Solution
Un module Migrations con una lista ordinata di step e onUpgrade che li applica; _onCreate diventa "applica tutti gli step da 0".
  • sblocca ogni cambio di schema futuro
  • testabile con DB in-memory (dipende da C2)
  • locality: DDL in un module
  • prerequisito se si vuole rinominare un dbKey

Senza quel seam nessun altro intervento è verificabile: la suite è un file su dead code, e C3, C4, C6 e C7 diventano tutti testabili solo dopo. È anche il più economico — l'interface esiste già dentro AppDatabase, va solo estratta e iniettata.
