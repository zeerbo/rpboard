# 04 — Single-item SessionScreen provider, SessionEditScreen, SessionPlayScreen, and ChapterScreen's rename call site

**What to build:** The `Database` seam gains `getScreen(String id)` — the same `where: 'id = ?'` shape as its sibling single-entity reads, implemented in `SqfliteDatabase` against the existing table and in the test-only `InMemoryDatabase` fake as a map lookup. On top of it, a `screenProvider(id)` joins the provider graph, backed by that new read and the existing `updateScreen`. `SessionEditScreen` stops loading its own SessionScreen by hand — today it fetches the whole screen list for its chapter and filters in memory — and instead `ref.watch(screenProvider(screenId))` for the header title it shows while editing components. `SessionPlayScreen` stops holding its own `setState`-loaded screen list and current-screen copy entirely: it keeps `ref.watch(screenListProvider(chapterId))` for the ordered set of screens it pages through and derives the currently displayed SessionScreen from that list by index, with only the page index remaining local UI state — no direct database call, no `initState`-driven load. `ChapterScreen`'s screen-rename dialog — today saving through `screenListProvider`'s notifier — moves its write to `screenProvider(id).notifier.save(...)`, which owns invalidating both itself and the parent `screenListProvider` for that screen's chapter. A DM renaming a "Scena" from the chapter's screen list sees the new title immediately in both the edit screen and while paging through play mode, with no stale copy anywhere it's shown. As a final regression check for the whole PRD, no remaining direct-to-seam update call or list-notifier save call for an existing Campaign/Chapter/SessionScreen/Character should exist outside the four single-item notifiers themselves.

**Blocked by:** atomic-reorder 03 — SessionScreen reorder becomes atomic, and atomic-reorder 04 — SessionComponent reorder becomes atomic (both rewrite `ChapterScreen` and `SessionEditScreen`, which this ticket also touches); plus tickets 01–03 of this PRD, since its final repo-wide regression check can only pass once every other single-item provider exists.
