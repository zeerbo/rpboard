# Single-item providers for Campaign / Chapter / SessionScreen / Character

Implements architecture-review candidate **C4** (`docs/architecture-review.html#c4`). Depends on [ADR-0002](../../docs/adr/0002-database-seam.md) (C2, done) — the `Database` seam and `databaseProvider` are the prerequisite this PRD builds on. A new ADR-0004 records the accepted decision. Sequenced C1 → C5 → C3 → **C4** → C6 → C7; C7 (decomposing `CharacterSheetScreen`) depends on this PRD landing first.

## Problem Statement

Every screen that shows a single Campaign, Chapter, SessionScreen, or Character loads it by hand in `initState`: it calls the *list* query for the parent collection through the `Database` seam, filters the result down to the one entity it wants in memory, and parks that entity in `setState`. That copy lives entirely outside the Riverpod provider graph. Nothing invalidates it, so it goes stale the moment the entity changes anywhere else — the screen holding it has no way to find out.

The sharpest, user-visible version of this bug lives in PG Mode. `CharacterSheetScreen` debounce-saves the Character a player is editing straight through `ref.read(databaseProvider).updateCharacter(...)`, bypassing every provider. It then invalidates `characterListProvider` as an afterthought, but the pattern is fragile and asymmetric: the write bypasses the provider layer while only the list read goes through it. Any other place reading that Character by id has no notifier to watch and no signal that a save happened.

Four Master Mode screens carry the same shape for Campaign, Chapter, and SessionScreen: `CampaignScreen`, `ChapterScreen`, `SessionEditScreen`, and `SessionPlayScreen` all fetch a full list through the seam, filter it in memory for the one row the route id names, and hold that row in `setState` for the lifetime of the screen.

## Solution

Add four single-item providers — `campaignProvider`, `chapterProvider`, `screenProvider`, `characterProvider` — each keyed by the entity's id. Each reads exactly one entity through the `Database` seam and each becomes the one writer for updates to an existing entity of its kind: renaming a Chapter, editing Campaign info, and autosaving a Character all move from ad hoc direct-to-seam writes to a call on the matching single-item provider's `save()`. A save invalidates itself and the parent list provider, so the two are never allowed to drift apart again — there is exactly one place a mutation of an existing entity can be made, and every reader downstream of the provider graph sees it.

The five screens named above stop holding their entity in `setState`. They `ref.watch` the corresponding single-item provider and render its `AsyncValue` directly — loading, error, or a `null` for a missing entity (a legitimate state, e.g. after a cascade delete elsewhere).

SessionComponent gets no such provider: it has no route id of its own and is only ever rendered as part of a list (`componentListProvider(screenId)`), so component saves keep going through the list notifier exactly as today.

## User Stories

1. As a developer, I want a `campaignProvider(id)`, `chapterProvider(id)`, `screenProvider(id)`, and `characterProvider(id)` — each an `AsyncNotifierProvider.family<..., String>` — so that a single entity has a first-class place in the provider graph instead of being an unmanaged `setState` copy.
2. As a developer, I want each single-item provider's `build(id)` to read its entity through the `Database` seam, so that the read goes through the same override point (`databaseProvider`) as every other provider in the app.
3. As a developer, I want each single-item provider's `save(entity)` to write through the seam, call `invalidateSelf()`, and invalidate the parent list provider's matching family entry, so that a caller never has to remember to invalidate two places by hand.
4. As a developer, I want `getChapter(String id)` and `getScreen(String id)` added to the `Database` interface (mirroring the `getCampaign`/`getCharacter` that already exist), so that all four single-item providers have a single-entity read to call instead of fetching and filtering a list.
5. As a developer, I want a missing entity to be a legitimate, handled state (`null`) rather than an exception, so that a screen opened right after its entity was cascade-deleted elsewhere fails gracefully instead of crashing.
6. As a developer maintaining `CampaignScreen`, I want it to `ref.watch(campaignProvider(campaignId))` instead of loading the campaign by hand in `initState`, so that editing the campaign elsewhere is reflected without a manual reload.
7. As a developer maintaining `ChapterScreen`, I want it to `ref.watch(chapterProvider(chapterId))` instead of fetching the full chapter list and filtering, so that a rename made from this screen or another is never stale.
8. As a developer maintaining `SessionEditScreen`, I want it to `ref.watch(screenProvider(screenId))` for the screen's own title/metadata, so that its `initState` no longer duplicates a list read it doesn't otherwise need.
9. As a developer maintaining `SessionPlayScreen`, I want it to keep watching `screenListProvider(chapterId)` for pagination across screens and derive the current SessionScreen from that list, with only the current page index staying as local UI state, so that the pagination model is unchanged while stale single-entity state is eliminated.
10. As a developer, I want the rename/save call sites for Chapter, SessionScreen, and Campaign rewritten to call `xProvider(id).notifier.save()` instead of `xListProvider(...).notifier.save()` or a direct seam write, so that there is exactly one writer per entity and the list notifiers keep only collection operations (`add`, `delete`, and C3's `reorder`).
11. As a developer, I want `CharacterSheetScreen`'s debounce-save to call `characterProvider(id).notifier.save()` instead of `ref.read(databaseProvider).updateCharacter(...)`, so that a save is visible to every provider watching that Character, including `characterListProvider`, without a manual `ref.invalidate` afterthought.
12. As a developer, I want the debounce interval and the dispose-time flush in `CharacterSheetScreen` left exactly as they are today, so that this change touches only the write target, not the autosave timing behavior.
13. As a developer, I want no `componentProvider` introduced, so that SessionComponent — which has no route id and is always rendered from `componentListProvider(screenId)` — keeps its existing, already-correct access pattern.
14. As a DM using Master Mode, I want a Chapter or SessionScreen rename made in one place to show up immediately everywhere else it's displayed, so that I never see a stale title while preparing or running a session.
15. As a DM, I want opening a Campaign, Chapter, or SessionScreen that was just deleted elsewhere (e.g. via a cascade from deleting its parent) to show a clear missing/error state instead of a crash or a silently frozen screen.
16. As a player in PG Mode, I want an edit I make on my Character sheet to be reflected immediately in the character list, so that switching back to "my characters" never shows an old name, level, or HP value.
17. As a developer picking up C7 (decomposing `CharacterSheetScreen`), I want the Character write path already routed through `characterProvider(id).notifier.save()`, so that C7 can split the screen's tabs without also having to fix the save path at the same time.
18. As a developer writing tests for these providers, I want a `ProviderContainer` overriding `databaseProvider` with `InMemoryDatabase`, matching the existing `test/providers/*_test.dart` pattern, so that the new families are tested the same way the list notifiers already are, with no new test seam to learn.

## Implementation Decisions

- **Four new providers, one per entity with a route id.** `campaignProvider`, `chapterProvider`, `screenProvider`, and `characterProvider`, each an `AsyncNotifierProvider.family<Notifier, Entity?, String>` keyed by the entity's id. No `componentProvider` — SessionComponent has no route id and no dedicated screen, so it stays exclusively behind `componentListProvider(screenId)`.
- **`build(id)` reads one entity through the seam.** Each notifier's `build` calls the matching single-entity `Database` method (`getCampaign`, `getChapter`, `getScreen`, `getCharacter`) and returns whatever it gets back, including `null`.
- **`AsyncNotifierProvider.family`, not read-only `FutureProvider.family`.** A `FutureProvider` was considered and rejected: mutations would have stayed on the list notifiers, leaving two places (list notifier and single-item provider) that would need to keep invalidating each other forever. An `AsyncNotifierProvider` gives each entity a `save()` that owns its own invalidation, and the list provider's invalidation is the one thing that `save()` triggers as a side effect, not a second independent write path.
- **`save(entity)` writes, then invalidates itself and the parent list.** Each notifier's `save` calls the matching `Database` update method, then `ref.invalidateSelf()`, then invalidates the parent list provider's family entry for this entity (e.g. saving a Chapter invalidates `chapterListProvider(campaignId)`). This is the mechanism that fixes the stale-list bug: a save is never visible in only one place.
- **The seam gains two read methods.** `Database.getChapter(String id)` and `Database.getScreen(String id)` are added, implemented in `SqfliteDatabase` (a `where: 'id = ?'` query, matching the existing `getCampaign`/`getCharacter` shape) and in `InMemoryDatabase` (a map lookup, matching its existing `getCampaign`/`getCharacter`). `getCampaign` and `getCharacter` already exist and are reused as-is.
- **A missing entity is a legitimate, typed state, not an error.** All four single-item `Database` reads return a nullable entity. A screen watching the provider must render the `null` case explicitly (e.g. after a cascade delete removed the entity out from under an open screen) rather than assuming the entity always exists.
- **The writer rule — the core decision of this PRD.** List notifiers (`campaignListProvider`, `chapterListProvider`, `screenListProvider`) keep collection-shaped operations only: `add`, `delete`, and (from C3) `reorder`. Every update to an *existing* Campaign, Chapter, SessionScreen, or Character goes through `xProvider(id).notifier.save()` instead. This rewrites today's call sites: Chapter rename (`ChapterScreen._renameChapter` via `campaign_provider.dart`'s `ChapterListNotifier.save`) and SessionScreen rename (`ChapterScreen._renameScreen` / wherever the equivalent lives for screens) move to `chapterProvider(id).notifier.save()` / `screenProvider(id).notifier.save()`; Campaign info edits (`CampaignScreen._saveInfo`, currently `campaignListProvider.notifier.save`) move to `campaignProvider(id).notifier.save()`; the Character autosave (`CharacterSheetScreen._saveNow`, currently a direct `ref.read(databaseProvider).updateCharacter(...)` call) moves to `characterProvider(id).notifier.save()`. One writer per path means no cross-invalidation to remember by convention.
- **`componentListProvider.notifier.save()` is unchanged.** The writer rule applies only to entities that have a single-item provider. SessionComponent updates (e.g. `SessionEditScreen`'s `onUpdate` callback) keep calling `componentListProvider(screenId).notifier.save(c)` exactly as today.
- **Screens watch instead of holding `setState` copies.** `CampaignScreen`, `ChapterScreen`, `SessionEditScreen`, and `CharacterSheetScreen` replace their `initState`-driven `_loadX()` + `setState` pattern with `ref.watch(xProvider(id))`, rendering the resulting `AsyncValue` (loading / error / data, with a `null` data value handled as "missing").
- **`SessionPlayScreen` keeps its list-based pagination.** It continues to `ref.watch(screenListProvider(chapterId))` for the ordered set of screens it pages through, and derives the currently displayed SessionScreen from that list by index. Only the current page index remains local UI state; the screen does not additionally watch `screenProvider(screenId)` for the current entity, since the list it already watches is a strictly more complete source for this screen's needs (adjacent-screen titles, count, ordering).
- **`CharacterSheetScreen`'s debounce mechanism is untouched.** The `Timer`-based 600ms debounce and the dispose-time flush (`_saveNow()` called from `dispose()`) stay exactly as implemented; only the call inside `_saveNow()` changes its target from the seam to `characterProvider(widget.characterId).notifier.save(_char!)`.
- **No schema change.** No table, column, or DDL changes. This is a provider-layer and call-site refactor only.
- **No user-visible change other than staleness going away.** Screens render the same information in the same layout; the only observable difference is that lists no longer show stale data after a save made elsewhere.
- **ADR-0004.** A new ADR records the accepted decision: four single-item `AsyncNotifierProvider.family`s, the seam additions (`getChapter`, `getScreen`), and the writer rule, noting its relationship to ADR-0002 (the seam this depends on) and its role as a prerequisite for C7.

## Testing Decisions

- **Pure-Dart `ProviderContainer` tests, no widget pump.** Each new family gets a test file under `test/providers/`, following the exact pattern already used by `test/providers/campaign_provider_test.dart` and its siblings: a `ProviderContainer` overriding `databaseProvider` with `InMemoryDatabase`. No new test seam is introduced.
- **Per family, at minimum:** `build(id)` returns the correct entity for a known id; `build(id)` for an unknown id returns the null/missing state without throwing; `save()` is observable on a subsequent read of the same provider; and — the regression test for the Character staleness bug — after `save()`, re-reading the *parent list* provider (`campaignListProvider`, `chapterListProvider(campaignId)`, `screenListProvider(chapterId)`, `characterListProvider`) reflects the change. This last assertion is the anti-stale guarantee this whole PRD exists to establish, and it is required for all four families, not just Character.
- **Assert external behavior only.** Tests check what a subsequent read returns — the value in the `AsyncValue`, the contents of a re-read list. They must not assert on invalidation call counts, listener registration, or private notifier fields, matching the discipline already established in ADR-0002's test suite.
- **No widget tests in this PRD.** Screen-level `ConsumerState` changes (swapping `setState` for `ref.watch`) are exercised only indirectly, through the provider tests above. Pumped-widget tests for the affected screens remain future work, consistent with C2's PRD deferring the same call.

## Out of Scope

- **`componentProvider`.** SessionComponent has no route id and is always rendered from a list; it is not part of this PRD's writer rule and gets no single-item provider.
- **Splitting the `Database` seam into per-aggregate repositories.** This PRD adds two methods (`getChapter`, `getScreen`) to the existing single interface; it does not restructure the seam itself.
- **C7's decomposition of `CharacterSheetScreen`.** This PRD only redirects the screen's save path to `characterProvider(id).notifier.save()`; splitting the 7-tab screen into smaller pieces is C7's job and depends on this PRD landing first.
- **C3's `reorder` operation.** The list notifiers' future `reorder` method is C3's concern; this PRD only confirms that reorder (like `add`/`delete`) stays a list-notifier, collection-shaped operation, not a single-item one.
- **C6's schema migrations.** No schema or DDL change is made here.
- **C1's typed `ComponentData`.** Orthogonal — this PRD does not touch the `SessionComponent.data` payload representation.

## Further Notes

- This PRD is the direct fix for the review's most concrete, user-visible bug: `CharacterSheetScreen` debounce-saving straight through the seam while `characterListProvider` silently falls behind. Every other screen touched here (`CampaignScreen`, `ChapterScreen`, `SessionEditScreen`) has the identical shape of bug, just less immediately visible because those screens are revisited less continuously during a session than the Character sheet is during play.
- Blast radius: one `Database` interface gets two new methods (implemented in both adapters); four new provider files (or four new sections in existing provider files, following `campaign_provider.dart`'s per-entity section convention); five screens swap `initState`-loaded `setState` fields for `ref.watch`; the handful of rename/save call sites named above move their writes from list notifiers or the raw seam onto the new single-item notifiers.
- Sharpest risk to watch during implementation: forgetting a call site. Because the writer rule changes *which* provider owns a save, any call site not migrated (e.g. a rename dialog left calling the old list notifier's `save`) will silently keep writing outside the new invalidation path and reintroduce exactly the staleness this PRD removes. A worthwhile follow-up check after implementation: grep for remaining `ref.read(databaseProvider).update*` and `xListProvider(...).notifier.save(` call sites outside the four new notifiers themselves.
